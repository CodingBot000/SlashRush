## 1. 리팩토링 원칙

현재 제품은 이미 제출된 상태이므로 첫 리팩토링 목표는 기능 추가가 아니라 동작 보존이다. 기획서 기준으로 보존해야 할 핵심 동작은 다음이다.

- `IntroScene -> MainMenu -> RunnerStage 60초 -> BossStage -> ResultPanel` 흐름
- Tap, Tap Tap, Hold, No Input 판정과 입력 회복 시간
- `enemy_basic`, `enemy_fast`, `enemy_armor`, `bomb`, `coin`, `heal`, `fever_orb` 규칙
- 러너 스폰 스케줄, 아이템 예산, 피버 러시 스폰
- 러너 피버와 보스 피버의 입력 완화, 점수, 연출 차이
- 보스 1/2페이즈 패턴 덱과 WAIT 패턴 규칙
- `user://save.cfg`, `user://settings.cfg` 저장 형식
- Web/Android export 설정과 Autoload 이름

리팩토링 중 우선 변경하지 말아야 할 것은 밸런스 수치, 신호 이름, 씬 경로, Autoload 이름, 저장 키, 테스트 스크립트 진입점이다. 구조 변경은 작게 나누고, 각 단계마다 기존 dev 테스트를 통과시킨다.

추가 검토 결과, 이 프로젝트의 장기 구조는 `RunnerStage`와 `BossStage`를 "1회용 stage1 구현"이 아니라 여러 스테이지에서 반복 사용하는 템플릿으로 보는 쪽이 맞다. 따라서 리팩토링 방향은 단순히 파일을 잘게 나누는 것보다 다음 목표를 포함해야 한다.

- `RunnerStage`와 `BossStage`는 재사용 가능한 실행기(scene/controller)로 유지한다.
- 스테이지별 배경, 플레이어 표시, 적/몬스터 시각 세트, 보스 시각, 속도감, 출현 밸런스는 stage config 데이터로 분리한다.
- 현재 선택된 캐릭터, 한 판에서 이어지는 score/coin/hp, 클리어한 스테이지 목록 같은 전역 공유 상태는 명시적인 session/progress 모델로 관리한다.
- 전역 상태를 아무 파일에서나 직접 수정하지 않고, `Main` 또는 전용 store가 상태 변경 경계를 갖게 한다.

### 2-2. 이미 좋은 분리

- `scripts/spawn/SpawnBalance.gd`, `NormalScheduleGenerator.gd`, `ItemSpawnRules.gd`, `FeverSpawner.gd`, `StageSpawnDirector.gd`는 급하게 만든 프로젝트치고는 스폰 책임이 이미 분리되어 있다.
- `RunnerFeverMode.gd`, `BossFeverMode.gd`, `PlayerLifeState.gd`는 독립 규칙 객체로 분리되어 있어 다음 리팩토링의 기준점으로 삼을 수 있다.
- `AudioHooks.gd`, `HapticHooks.gd`는 Autoload 직접 의존을 감싸는 좋은 패턴이다. 같은 방식으로 DebugFlags, 저장소, 리소스 로더를 감싸면 된다.

### 2-3. 다중 스테이지 관점에서의 부족한 지점

현재 구현은 stage1 제출본에 최적화되어 있어 다음 값들이 코드에 직접 박혀 있다.

- `ParallaxScroller.gd`: stage1 하늘/구름/원경/중경/근경 텍스처 경로와 스크롤 계수
- `GroundLooper.gd`: stage1 ground texture와 속도 전제
- `BossStage.gd`: 보스 배경, 보스 파츠, 보스 패턴 덱, scrap texture, cue texture
- `PlayerController.gd`: 현재 플레이어 스프라이트 경로와 러닝/피격/사망/무기 레이어
- `ObjectTypes.gd`: 오브젝트 규칙과 stage1 오브젝트 시각 자산
- `SpawnBalance.gd`: stage1 60초 러너 구간의 phase/interval/item budget
- `GameBalance.gd`: 전역 상수와 stage1 속도감 상수가 섞임

따라서 다음 스테이지를 추가하려면 파일을 복사하거나 조건문을 늘리게 될 위험이 크다. 리팩토링 목표는 이 하드코딩을 `StageDefinition` 계열 데이터로 이동시키는 것이다.

## 3. 코드 중복 후보

다음 항목은 먼저 유틸로 빼도 동작 리스크가 낮다.

- 텍스처 로드: `_load_texture()`가 `PlayerController`, `ParallaxScroller`, `GroundLooper`, `BossStage`, `IntroScene`, `MainMenu`, `HowToScreen`, `CharacterSelect`, `ResultPanel`, `ComboImpactPopup` 등에 반복됨
- viewport fallback: `_get_viewport_size()`가 `ParallaxScroller`, `GroundLooper`, `BossStage`, `FeverImpactOverlay`에 반복됨
- InputMap 등록/삭제: `Main.gd`와 `RunnerStage.gd` 단독 실행 코드에 `_add_action_if_missing`, `_add_key_event`, `_action_has_key`, `_action_has_mouse`, `_remove_mouse_event` 중복
- DebugFlags 접근: `/root/DebugFlags` 조회가 `Main`, `RunnerStage`, `BossStage`, `GameHUD`, `SettingsPopup`에 분산됨
- 액션 매칭: `tap` 대상에 `double_tap` 허용하는 `_action_matches()`가 `RunnerStage`, `BossStage`에 중복됨
- 노드 정리: `_clear_children()`가 `RunnerStage`, `BossStage`에 중복됨
- 전투 피드백 텍스트: 러너의 `_spawn_world_text()`는 스테이지에 묶여 있어 보스/다른 화면에서 재사용하기 어렵다

## 4. 데이터와 Godot 의존 분리 방향

### 4-1. 오브젝트 데이터 분리

`ObjectTypes.gd`는 현재 하나의 딕셔너리에 규칙과 시각 정보를 모두 반환한다.

권장 분리:

- `scripts/data/ObjectRuleCatalog.gd`
  - `required_action`, `is_good_item`, `score`, `fever`, `damage`
  - 색, 크기, 텍스처, shape를 포함하지 않음
  - 러너 판정과 테스트가 사용할 데이터
- `scripts/data/ObjectVisualCatalog.gd`
  - `color`, `label`, `size`, `shape`, `texture`, `slice_texture`, `spawn_y_offset`
  - `InteractableObject`, HOW TO 카드, 시각 이펙트가 사용할 데이터
- `scripts/data/ObjectTypes.gd`
  - 당분간 compatibility facade로 유지
  - `get_data()`는 두 catalog 결과를 합쳐 기존 호출부가 깨지지 않게 함
  - `get_spawn_type()`은 참조가 없으므로 테스트 확인 후 제거 또는 `LegacyObjectSpawnPattern.gd`로 이동

이 분리만 해도 "게임 규칙 변경"과 "스프라이트/크기 변경"이 독립된다.

### 4-2. 액션/판정 규칙 분리

문자열 `"tap"`, `"double_tap"`, `"long_tap"`, `"no_input"`이 여러 파일에 직접 흩어져 있다.

권장 파일:

- `scripts/data/ActionTypes.gd`
  - 액션 문자열 상수
  - `matches(required, actual, fever_active := false)` 제공
  - `get_hint(action)` 제공

이후 `RunnerStage._action_matches`, `BossStage._action_matches`, `ObjectTypes.get_action_hint`를 하나로 합친다.

### 4-3. 저장 데이터 분리

`Main.gd`와 `MainMenu.gd`가 `user://save.cfg`를 직접 읽고, 테스트도 같은 경로를 직접 건드린다.

권장 파일:

- `scripts/save/ProgressStore.gd`
  - `load_progress() -> Dictionary`
  - `save_progress(best_score, total_coins) -> void`
  - 저장 섹션/키를 한 곳에서 관리
- `scripts/settings/GameSettings.gd`
  - 현재 설정 저장소 역할을 이미 포함하므로 유지
  - 필요하면 내부 ConfigFile 접근만 `SettingsStore.gd`로 추출

저장소를 빼면 메인 플로우 테스트에서 저장 파일 백업/복구도 더 작게 만들 수 있다.

### 4-4. 스테이지 정의 데이터 분리

`RunnerStage`와 `BossStage`가 반복 사용될 예정이면 "어떤 스테이지를 플레이하는가"를 나타내는 데이터가 필요하다. 권장 구조는 다음과 같다.

- `scripts/data/stage/StageCatalog.gd`
  - stage id로 `StageDefinition` 조회
  - 예: `stage_1_forest`, `stage_2_castle` 같은 식별자
- `scripts/data/stage/StageDefinition.gd`
  - `id`, `display_name`
  - `runner_config`
  - `boss_config`
  - `unlock_condition`
  - `next_stage_id`
- `scripts/data/stage/RunnerStageConfig.gd`
  - 배경 레이어 텍스처와 패럴랙스 factor
  - ground texture, scroll speed, object speed, fever speed multiplier
  - 스폰 phase, item budget, fever rush weights
  - 해당 스테이지에서 등장 가능한 적/아이템 role
- `scripts/data/stage/BossStageConfig.gd`
  - 보스 배경
  - 보스 씬 또는 visual profile
  - phase별 패턴 덱 구성
  - 보스 HP, 점수, 피버 수치
  - hit scrap texture set, cue visual profile
- `scripts/data/stage/CharacterVisualProfile.gd`
  - 현재 선택된 캐릭터의 run/idle/damage/dead/weapon texture
  - 캐릭터별 크기 보정과 위치 보정
- `scripts/data/stage/ObjectVisualSet.gd`
  - 같은 `enemy_basic` 규칙을 쓰더라도 스테이지마다 다른 몬스터 스프라이트를 매핑
  - 예: `enemy_basic -> scarecrow` 또는 `enemy_basic -> skeleton`

중요한 분리 기준:

- `enemy_basic`이 Tap으로 처리되고 점수 100을 주는 것은 rule catalog의 책임이다.
- `enemy_basic`이 stage1에서는 허수아비, stage2에서는 해골 병사로 보이는 것은 visual set의 책임이다.
- 러너의 실행 방식은 `RunnerStage`에 남기되, 속도/스폰/배경/적 세트는 `RunnerStageConfig`에서 주입한다.

### 4-5. 세션 상태와 영구 진행 상태 분리

전역 공유 상태는 두 종류로 나눠야 한다.

런타임 세션 상태:

- 현재 run id
- 현재 선택된 stage id
- 현재 선택된 character id
- 러너에서 보스로 이어지는 score, run coins, hp
- 현재 구간: runner, boss, result

영구 진행 상태:

- 선택된 character id
- 누적 coin
- 최고 score
- 클리어한 stage id 목록
- 해금된 character/stage 목록

권장 파일:

- `scripts/state/GameSessionState.gd`
  - 한 번의 플레이 흐름에서만 유지되는 상태
  - `Main.gd`가 만들고 `RunnerStage`/`BossStage`에 필요한 값만 전달하는 방식이 가장 안전
  - Autoload로 둘 경우에도 직접 수정 API를 제한해야 함
- `scripts/save/ProgressStore.gd`
  - `user://save.cfg` 저장/로드
  - `best_score`, `total_coins`, `selected_character_id`, `cleared_stage_ids`를 관리
- `scripts/state/ProgressState.gd`
  - 저장소에서 읽은 영구 진행 데이터의 메모리 표현

현재 `Main.gd`의 `current_score`, `current_coins`, `current_hp`, `best_score`, `total_coins`는 위 구조로 이동할 후보이다. `Main`은 상태를 직접 보관하기보다 stage flow를 진행하고, state/store를 통해 값을 갱신하는 조정자 역할을 맡는다.

## 5. 역할 분리 세부 계획

### 5-1. RunnerStage 분리

목표는 `RunnerStage.gd`가 "오케스트레이터"만 맡게 만드는 것이다. 다중 스테이지를 고려하면 `RunnerStage`는 stage1 전용 씬이 아니라 `RunnerStageConfig`를 받아 실행되는 재사용 가능한 러너 실행기여야 한다.

추출 후보:

- `scripts/game/runner/RunnerStageContext.gd`
  - `stage_id`, `runner_config`, `character_profile`, `object_visual_set`, 시작 score/coin/hp
  - `start_run(context)` 또는 `configure(context)`의 입력값
- `scripts/game/runner/RunnerCombatResolver.gd`
  - 오브젝트 타입, 요구 액션, 현재 액션, 피버 여부를 받아 결과를 반환
  - 결과 예: `success`, `prompt`, `fail`, `break_good_item`, `collect_good_item`
- `scripts/game/runner/RunnerRunState.gd`
  - `score`, `coins`, `hp`, `combo`, `run_elapsed` 보관
  - 성공/실패/획득에 따른 숫자 변경 담당
- `scripts/game/runner/ActionZoneQuery.gd`
  - 액션존 안의 오브젝트 찾기, 가장 가까운 오브젝트 찾기
  - Godot 노드 의존은 있지만 판정 로직을 Stage에서 분리
- `scripts/effects/WorldTextFactory.gd`
  - `+100`, `MISS`, `BROKEN`, `HOLD` 같은 월드 텍스트 생성
- `scripts/effects/ImpactFeedback.gd`
  - hitstop, shake 시작/업데이트를 재사용 가능한 컴포넌트로 분리

첫 단계에서는 public signal과 `start_run()`, `stop_run()`, `handle_player_action()`, `debug_fill_fever()` 시그니처를 유지한다.

그 다음 단계에서 `start_run()`을 바로 깨지 말고 `configure(context)`를 먼저 추가한다. 기존 테스트는 context가 없으면 stage1 기본 config를 쓰게 하여 유지한다.

### 5-2. BossStage 분리

보스전은 러너보다 오브젝트 스폰이 없으므로 패턴과 표시를 먼저 빼는 것이 안전하다. 다중 스테이지를 고려하면 `BossStage`도 `BossStageConfig`를 받아 배경, 보스 visual, 패턴 덱, 보상 수치를 바꾸는 재사용 실행기여야 한다.

추출 후보:

- `scripts/game/boss/BossStageContext.gd`
  - `stage_id`, `boss_config`, `character_profile`, 시작 score/coin/hp
- `scripts/game/boss/BossPatternConfig.gd`
  - 페이즈별 Tap/Tap Tap/Hold/Wait 개수
  - 패턴 시간과 pattern code 매핑
- `scripts/game/boss/BossPatternDeck.gd`
  - 덱 생성, shuffle, phase별 next pattern
- `scripts/game/boss/BossCombatState.gd`
  - boss hp, player hp, score, combo, fever gain 계산
- `scripts/ui/BossPatternCueView.gd`
  - 원형 큐, WAIT 큐, 타이머 바 표시
- `scripts/game/boss/BossBackgroundView.gd`
  - 배경 fill/sprite, 회전, viewport layout

`RobotSamuraiBoss.gd`는 일단 유지한다. 이후 공격별 수치와 pose 함수를 `BossMotionConfig.gd` 또는 `RobotSamuraiBossMotion.gd`로 뺄 수 있다.

보스 종류가 늘어날 가능성이 있으면 `RobotSamuraiBoss.gd`를 직접 참조하지 않고 `BossStageConfig.boss_scene_path` 또는 `boss_visual_profile`로 선택하게 만든다. 단, 첫 리팩토링에서는 stage1 로봇 사무라이를 기본값으로 유지한다.

### 5-3. UI 분리

제출 직전에는 코드 생성형 UI가 빠르지만, 리팩토링 이후에는 데이터/스타일/상호작용을 나눈다.

우선순위:

- `scripts/ui/common/UiTextureLoader.gd` 또는 공통 `ResourceLoadUtil.gd` 사용
- `scripts/ui/common/UiLabelFactory.gd`, `UiButtonFactory.gd`는 중복이 누적될 때만 도입
- `HowToScreen.CARD_DATA`를 `scripts/data/HowToCardData.gd`로 분리
- `CharacterSelect.characters`를 `scripts/data/CharacterCatalog.gd`로 분리
- 드래그 스크롤 처리는 `HorizontalDragScroll.gd`로 분리 가능

과도한 UI 추상화는 피하고, 실제 중복이 있는 label/button/drag 정도만 뺀다.

### 5-4. 유틸 파일 후보

우선 만들 가치가 높은 유틸:

- `scripts/utils/ResourceLoadUtil.gd`
  - `load_texture(path)`, `load_audio_stream(path)` 후보
  - 단, `AudioManager`의 loop 설정은 유지

  - `is_player_invincible(owner)`, `should_start_in_boss(owner)`

### Phase 0. 기준선 고정

### Phase 1. 저위험 유틸 추출

목표: 코드 중복을 줄이되 게임 규칙을 건드리지 않는다.

- `ResourceLoadUtil`, `ViewportUtil`, `InputMapUtil`, `DebugFlagsAccess`, `NodeUtil` 추가
- 기존 중복 함수는 한 파일씩 대체
- 각 파일 변경 후 관련 dev 테스트 실행

- `scripts/Main.gd`

- `scripts/game/BossStage.gd`

- `scripts/game/GroundLooper.gd`
- `scripts/effects/FeverImpactOverlay.gd`
- `scripts/ui/*.gd`
- `scripts/player/PlayerController.gd`

### Phase 2. 데이터 catalog 분리

목표: 게임 규칙 데이터와 시각 데이터를 분리한다.

- `ObjectRuleCatalog.gd`, `ObjectVisualCatalog.gd`, `ActionTypes.gd` 추가
- `ObjectTypes.gd`는 facade로 유지
- `InteractableObject.gd`는 visual catalog 의존으로 점진 이동
- `RunnerStage`, `BossStage` 액션 매칭은 `ActionTypes.matches()` 사용
- `ObjectTypes.get_spawn_type()` 제거 가능 여부를 테스트로 확인

### Phase 3. 스테이지 config와 전역 상태 도입

목표: `RunnerStage`/`BossStage` 재사용을 위한 데이터 주입 경계를 만든다.

- `StageCatalog`, `StageDefinition`, `RunnerStageConfig`, `BossStageConfig` 추가
- stage1 현재 값을 config 기본값으로 옮기되 기존 파일 facade를 유지
- `GameSessionState`, `ProgressStore`, `ProgressState` 추가
- `Main.gd`의 score/coin/hp/best_score/total_coins 보관 책임을 session/progress로 이동할 준비
- `CharacterSelect`의 선택값을 `selected_character_id`로 저장할 경로 마련
- `cleared_stage_ids` 저장 키를 추가하되, 기존 save 파일이 없어도 기본값 `[]`로 동작하게 함

이 단계에서는 실제 스테이지 선택 UI를 만들지 않는다. stage1만 catalog에 등록하고, 이후 stage2 추가가 쉬운 구조를 만든다.

### Phase 4. RunnerStage 축소

목표: 847줄짜리 스테이지 파일을 상태/판정/연출 컴포넌트로 분리한다.

- 액션존 쿼리와 액션 매칭 분리
- 성공/실패/좋은 아이템 처리의 숫자 계산을 `RunnerRunState` 또는 `RunnerCombatResolver`로 이동
- world text와 hitstop/shake를 effects 컴포넌트로 이동
- `RunnerStage`는 Node 생성, signal 연결, 컴포넌트 호출만 담당하도록 축소
- 배경/ground/player/object/spawn balance는 `RunnerStageContext`에서 받은 config로 구성

이 단계는 가장 위험하므로 한 번에 큰 이동을 하지 않는다. 먼저 읽기 전용 helper 추출, 그 다음 state mutation 추출 순서로 진행한다.

### Phase 5. BossStage 축소

목표: 보스 패턴/큐/배경/전투 계산을 분리한다.

목표: 화면별 프로토타입 데이터와 UI 생성 코드를 분리한다.

## 8. 첫 실제 작업 추천

가장 먼저 할 커밋은 다음 정도가 적절하다.

1. `ResourceLoadUtil`, `ViewportUtil`, `NodeUtil` 추가
2. `ParallaxScroller`, `GroundLooper`, `BossStage`, `FeverImpactOverlay`의 viewport/clear/load 중복만 대체
3. 게임 규칙은 변경하지 않음
4. Godot headless와 smoke/spawn/boss cue 테스트 실행

그 다음 커밋에서 `ActionTypes`와 `ObjectRuleCatalog`를 도입한다. 이후 바로 `StageCatalog`/`StageDefinition`과 `GameSessionState`/`ProgressStore`를 도입해 stage1 값을 기본 config로 등록한다. 이 순서가 좋은 이유는 첫 커밋은 순수 중복 제거라 회귀 범위가 작고, 두 번째 커밋부터 게임 규칙 경계와 스테이지 데이터 경계가 바뀌기 때문이다.

## 9. 보강 검토 결론

기존 문서는 코드 중복, 역할 분리, Godot 의존 제거 관점은 다루고 있었지만, 스테이지 반복 사용과 전역 공유 상태 설계는 충분하지 않았다. 이 보강 이후 리팩토링의 핵심 방향은 다음으로 정리된다.

- `RunnerStage`와 `BossStage`는 재사용 실행기로 남긴다.
- stage1 고정값은 `StageDefinition` 하위 config로 이동한다.
- 배경, 플레이어, 적몬스터, 보스, 속도감, 스폰 밸런스는 스테이지별 데이터로 바꾼다.
- 현재 선택 캐릭터, 진행 중 score/coin/hp는 `GameSessionState`로 관리한다.
- 누적 coin, 최고 score, 선택 캐릭터, 클리어한 스테이지는 `ProgressStore`로 관리한다.
- 현재 제출본 호환을 위해 stage1 기본값과 기존 save key는 유지하면서 새 필드는 기본값을 제공한다.
