# Slash Rush Unity 컨버전 전략

작성 시각: 2026-05-20 16:55:55 KST  
작성 기준:

- 현재 `main` 브랜치의 Godot 4.6.2 프로젝트

## 1. 결론

Unity 전환은 Godot 프로젝트를 1:1 파일 변환하는 방식이 아니라, 현재 게임의 규칙과 데이터 계약을 기준으로 Unity에서 재구현하는 방식이 안전하다. 특히 최근 리팩토링으로 분리된 `StageCatalog`, `RunnerStageConfig`, `BossStageConfig`, `GameSessionState`, `ProgressState` 구조를 Unity의 `ScriptableObject`와 C# 런타임 상태 클래스로 옮기면, stage1을 보존하면서 추후 스테이지와 에셋스토어 에셋 교체까지 자연스럽게 확장할 수 있다.

전환 우선순위는 다음이다.

1. Godot 제출본을 기준 동작으로 고정한다.
2. Unity에서 데이터 모델과 게임 플로우를 먼저 만든다.
3. 임시 에셋은 기존 Godot PNG/음원을 그대로 가져온다.
4. RunnerStage parity를 먼저 맞춘다.
5. BossStage parity를 맞춘다.
6. UI, 저장, 오디오, 햅틱, 설정을 붙인다.
7. 에셋스토어 에셋 교체가 가능하도록 Addressable/Prefab/Profile 경계를 유지한다.

## 2. 컨버전 목표와 비목표

### 목표

- `Intro -> MainMenu -> RunnerStage -> BossStage -> Result` 전체 흐름을 Unity에서 재현한다.
- Tap, Tap Tap, Hold, No Input 판정을 동일하게 보존한다.
- 러너 60초 스폰 스케줄, 아이템 예산, 피버 러시, 피격 슬로우를 재현한다.
- 보스 1/2페이즈 패턴 덱, WAIT 패턴, 보스 피버, 피격 scrap 연출을 재현한다.
- 현재 선택 캐릭터, 누적 코인, 최고 점수, 클리어 스테이지 목록을 Unity 저장소로 이전 가능한 형태로 만든다.
- stage1 임시 에셋은 기존 Godot 에셋을 사용하되, 추후 Asset Store 에셋으로 교체하기 쉬운 구조를 만든다.

### 비목표

- Godot `.tscn`, `.gd`, `.import`를 자동 변환하는 도구 개발은 하지 않는다.
- Godot와 Unity를 동시에 장기 운영하는 멀티엔진 구조는 만들지 않는다.
- 첫 Unity 버전에서 신규 스테이지, 신규 보스, 신규 캐릭터를 추가하지 않는다.
- 전환 초기부터 에셋스토어 최종 아트 품질을 목표로 하지 않는다.

## 3. 현재 Godot 구조에서 보존할 핵심 계약

Unity 전환 시 아래 항목은 먼저 고정해야 한다.

| 영역 | Godot 기준 | Unity 이전 단위 |
|---|---|---|
| 앱 플로우 | `Main.gd` | `GameFlowController` |
| 러너 실행기 | `RunnerStage.gd` | `RunnerStageController` |
| 보스 실행기 | `BossStage.gd` | `BossStageController` |
| 입력 판정 | `InputInterpreter.gd`, `ActionTypes.gd` | `InputInterpreter`, `ActionTypes` |
| 오브젝트 규칙 | `ObjectRuleCatalog.gd` | `ObjectRuleCatalog` 또는 `ObjectRuleSet` |
| 오브젝트 시각 | `ObjectVisualCatalog.gd`, `ObjectVisualSet.gd` | `ObjectVisualSet` ScriptableObject |
| 러너 설정 | `RunnerStageConfig.gd` | `RunnerStageConfig` ScriptableObject |
| 보스 설정 | `BossStageConfig.gd` | `BossStageConfig` ScriptableObject |
| 스테이지 목록 | `StageCatalog.gd`, `StageDefinition.gd` | `StageCatalog` ScriptableObject |
| 세션 상태 | `GameSessionState.gd` | `GameSessionState` C# class |
| 영구 진행 | `ProgressState.gd`, `ProgressStore.gd` | `ProgressState`, `ProgressStore` |
| 피버 | `RunnerFeverMode.gd`, `BossFeverMode.gd` | `RunnerFeverMode`, `BossFeverMode` |
| 스폰 | `NormalScheduleGenerator`, `ItemSpawnRules`, `FeverSpawner`, `StageSpawnDirector` | 동일 이름의 pure C# + MonoBehaviour adapter |

## 4. Unity 프로젝트 구조 제안

Godot 프로젝트를 바로 지우거나 덮어쓰지 말고, 같은 저장소 안에 별도 Unity 루트를 두는 방식을 권장한다.

```text
SlashRush/
  assets/                  # 기존 Godot 에셋 원본
  scenes/
  scripts/
  docs/
  unity/
    SlashRushUnity/
      Assets/
        SlashRush/
          Art/
            ImportedGodot/
            StoreReplacement/
          Audio/
          Prefabs/
          Scenes/
          Scripts/
          ScriptableObjects/
          Tests/
      Packages/
      ProjectSettings/
```

이 구조의 장점은 다음이다.

- Godot 제출본을 기준 구현으로 유지할 수 있다.
- Unity 전환 작업이 기존 Godot 프로젝트와 섞이지 않는다.
- 기존 에셋을 임시로 복사해도 `.import` 파일과 Unity `.meta` 파일이 충돌하지 않는다.
- 추후 완전히 Unity로 전환한 뒤 Godot 폴더를 아카이브하거나 제거하기 쉽다.

## 5. 에셋 이전 전략

### 5-1. 임시 에셋

초기 Unity 버전에서는 기존 Godot 에셋을 그대로 사용한다.

복사 대상:

- `assets/background/**/*.png`
- `assets/boss/**/*.png`
- `assets/characters/**/*.png`
- `assets/items/**/*.png`
- `assets/objects/**/*.png`
- `assets/sprites/**/*.png`
- `assets/ui/**/*.png`
- `assets/audio/**/*.mp3`
- `assets/audio/**/*.ogg`
- `assets/audio/**/*.wav`

복사 제외:

- `*.import`
- `.uid`
- `.DS_Store`
- Godot shader 파일은 Unity shader로 재작성 대상이다.

Unity import 설정:

- 2D Sprite 모드 사용
- UI 이미지는 `Sprite (2D and UI)`로 분리 관리
- pixel-perfect가 아니라 현재 제출본의 HD sprite 스케일링 감각을 우선한다.
- 배경/ground는 반복 배치와 wrap 처리가 필요하므로 texture repeat 가능 여부를 개별 확인한다.
- 음원은 Music/SFX mixer group을 나눠 관리한다.

### 5-2. 추후 Asset Store 교체를 위한 규칙

Asset Store 에셋을 구매해 교체할 계획이 있으므로, 코드에서 직접 특정 PNG 경로를 참조하지 않는다.

권장 경계:

- 캐릭터는 `CharacterVisualProfile` ScriptableObject로만 참조한다.
- 러너 배경은 `RunnerStageConfig.BackgroundLayers`로만 참조한다.
- 적/아이템 외형은 `ObjectVisualSet`으로만 참조한다.
- 보스는 `BossStageConfig.BossPrefab`, `BossHitScrapSprites`로만 참조한다.
- UI 아이콘은 `UiThemeConfig` 또는 화면별 serialized field로 참조한다.

교체 절차:

1. 새 에셋을 `Art/StoreReplacement/<asset_pack_name>/` 아래에 import한다.
2. prefab/profile만 새 에셋으로 교체한다.
3. 게임 규칙 코드는 수정하지 않는다.
4. Runner/Boss parity test를 다시 실행한다.

## 6. 데이터 모델 설계

Unity에서는 `ScriptableObject`를 stage/asset config에 사용하고, 런타임에서 변하는 값은 plain C# class로 둔다.

### 6-1. ScriptableObject

```text
StageDefinition
  string Id
  string DisplayName
  RunnerStageConfig Runner
  BossStageConfig Boss
  CharacterVisualProfile DefaultCharacter
  ObjectVisualSet ObjectVisuals
  string NextStageId
  UnlockCondition UnlockCondition

RunnerStageConfig
  float DurationSeconds
  float MapScrollSpeed
  float GroundScrollSpeed
  float ObjectSpeed
  float FeverDuration
  float FeverScrollSpeedMultiplier
  float FeverObjectSpeedMultiplier
  List<ParallaxLayerConfig> BackgroundLayers
  Sprite GroundSprite
  List<SpawnPhaseConfig> SpawnPhases
  ItemBudgetConfig ItemBudget
  FeverRushConfig FeverRush

BossStageConfig
  GameObject BossPrefab
  Sprite BossBackground
  int BossMaxHp
  int SuccessScore
  int FeverSuccessScore
  int ClearBonusScore
  BossPatternDeckConfig Phase1
  BossPatternDeckConfig Phase2
  List<Sprite> HitScrapSprites
```

### 6-2. 런타임 상태

```text
GameSessionState
  int RunId
  string StageId
  string SelectedCharacterId
  int CurrentScore
  int CurrentCoins
  int CurrentHp
  GamePhase Phase

ProgressState
  string SelectedCharacterId
  int TotalCoins
  int BestScore
  HashSet<string> ClearedStageIds
  HashSet<string> UnlockedCharacterIds
```

런타임 상태는 `MonoBehaviour`가 아니라 serializable C# class로 두는 것이 좋다. 이렇게 하면 테스트와 저장소 코드가 Unity scene lifecycle에 묶이지 않는다.

## 7. 씬 전환 전략

Unity 씬은 처음부터 Godot 씬 수와 1:1로 맞출 필요가 없다. 작은 게임이므로 `Bootstrap` 씬 하나에서 화면 prefab을 교체하는 방식이 더 안전하다.

권장 구조:

```text
Scenes/
  Bootstrap.unity

Prefabs/Screens/
  IntroScreen.prefab
  MainMenuScreen.prefab
  CharacterSelectScreen.prefab
  HowToScreen.prefab
  GameHud.prefab
  ResultPanel.prefab

Prefabs/Stages/
  RunnerStage.prefab
  BossStage.prefab
```

`GameFlowController`가 다음 흐름을 관리한다.

```text
Intro
  -> MainMenu
  -> RunnerStageContext 생성
  -> RunnerStageController.Configure(context)
  -> RunnerStageController.StartRun()
  -> BossStageContext 생성
  -> BossStageController.Configure(context)
  -> BossStageController.StartBoss()
  -> Result
```

장점:

- 모바일에서 씬 로드 비용과 초기화 순서를 통제하기 쉽다.
- Godot의 `Main.gd` 역할을 Unity에서 명확히 재현할 수 있다.
- stage prefab은 재사용하고 config만 바꿀 수 있다.

## 8. 시스템별 컨버전 계획

### 8-1. 입력

Unity 입력은 모바일 터치와 PC 테스트 입력을 같은 `InputInterpreter`로 흘려보낸다.

보존 규칙:

- Tap
- Tap Tap, 첫 탭 후 0.25초 안의 두 번째 탭
- Hold, 0.45초 이상
- 입력 회복 시간
- 피버 중 입력 회복 무시
- 피격 잠금 중 입력 초기화

Unity 구현:

- 초기에는 `Update()`에서 `Input.GetMouseButton*`와 touch를 함께 처리한다.
- 추후 필요하면 Unity Input System으로 이전하되, `InputInterpreter`의 public API는 유지한다.
- HUD 터치 영역은 `GraphicRaycaster` 또는 투명 `Button`이 아니라, gameplay touch area component로 별도 라우팅한다.

### 8-2. RunnerStage

`RunnerStageController`는 config를 받아 실행되는 재사용 stage runner가 되어야 한다.

구성 요소:

- `ParallaxScroller`
- `GroundLooper`
- `ObjectSpawnDirector`
- `RunnerFeverMode`
- `PlayerController2D`
- `ActionZoneQuery`
- `RunnerCombatResolver`
- `WorldTextSpawner`
- `SliceEffectFactory`

컨버전 순서:

1. 배경/ground 스크롤만 구현한다.
2. 플레이어 run/idle/damage/dead 상태를 구현한다.
3. 오브젝트 스폰 없이 수동으로 object prefab을 놓고 입력 판정을 맞춘다.
4. `NormalScheduleGenerator`를 C#으로 옮겨 60초 schedule을 재현한다.
5. `ItemSpawnRules`와 `FeverSpawner`를 붙인다.
6. 피버 속도감, hitstop, shake, world text를 붙인다.
7. Godot dev test 결과와 비교한다.

### 8-3. 오브젝트

Unity object prefab은 하나로 시작한다.

```text
InteractableObject.prefab
  SpriteRenderer
  Collider2D
  InteractableObject
  Optional visual effect component
```

`ObjectRule`은 입력/점수/피버/데미지만 가진다. `ObjectVisual`은 sprite, slice sprite, size, spawn offset만 가진다. 규칙과 외형을 분리해야 stage2 이후 몬스터 교체가 쉬워진다.

### 8-4. BossStage

`BossStageController`도 stage1 보스 전용이 아니라 `BossStageConfig`로 동작하는 실행기가 되어야 한다.

구성 요소:

- `BossStageController`
- `BossPatternDeck`
- `BossFeverMode`
- `BossCuePresenter`
- `BossVisualController`
- `BossHitScrapSpawner`
- `PlayerController2D`

컨버전 순서:

1. 보스 배경과 player/boss 배치를 구현한다.
2. 패턴 덱 생성과 Tap/Tap Tap/Hold/Wait 판정을 구현한다.
3. 보스 HP/점수/피버 수치를 config에서 읽게 한다.
4. 보스 파츠 모션은 처음에는 최소 idle/hit/dead만 구현한다.
5. 이후 Godot `RobotSamuraiBoss.gd` 모션을 Unity animation/tween 구조로 옮긴다.

### 8-5. UI

UI는 Unity Canvas 기반으로 재구성한다.

우선 구현:

- Intro
- MainMenu
- SettingsPopup
- GameHUD
- ResultPanel
- HowToScreen
- CharacterSelect

주의점:

- 현재 게임은 모바일 가로 1280x720 기준이다.
- Unity Canvas Scaler는 `Scale With Screen Size`, reference 1280x720을 기준으로 시작한다.
- GameHUD는 러너/보스 모드를 분리하되 같은 prefab에서 상태 전환한다.
- 디버그 버튼은 개발 빌드 조건 또는 debug flag로만 표시한다.

### 8-6. 저장/설정

Godot의 `user://save.cfg`, `settings.cfg`는 Unity에서 그대로 읽을 필요는 없다. 다만 키 의미는 보존한다.

Unity 저장 방식:

- 초기: `Application.persistentDataPath` 아래 JSON
- `progress.json`: selected character, best score, total coins, cleared stages
- `settings.json`: music volume, sfx volume, haptics, debug flags

마이그레이션이 필요하면 별도 importer를 만든다. 제출본 이후 새 Unity 앱으로 배포한다면 이전 Godot 저장 파일과의 호환은 필수 목표가 아니다.

### 8-7. 오디오/햅틱

Unity에서는 다음 구조를 권장한다.

- `AudioService`
  - Music AudioSource
  - SFX AudioSource pool
  - AudioMixer group: Music, SFX
- `HapticService`
  - Android/iOS native vibration wrapper
  - Editor에서는 no-op
- `AudioHooks`, `HapticHooks` 개념은 유지
  - 게임 로직이 구체 서비스 구현에 직접 묶이지 않게 한다.

## 9. 테스트 전략

Godot dev 테스트를 Unity PlayMode/EditMode 테스트로 대응시킨다.

| Godot 테스트 | Unity 대응 |
|---|---|
| `SpawnScheduleTest.gd` | `SpawnScheduleTests.cs` |
| `FeverModeBehaviorTest.gd` | `RunnerFeverModeTests.cs` |
| `BossAttackTimingTest.gd` | `BossAttackTimingTests.cs` |
| `BossPatternCueTest.gd` | `BossPatternDeckTests.cs`, `BossCuePresenterTests.cs` |
| `ResultPanelTest.gd` | `ResultPanelPresenterTests.cs` |
| `MainMenuProgressTest.gd` | `ProgressStoreTests.cs` |
| `CharacterSelectTest.gd` | `CharacterSelectPresenterTests.cs` |
| `StageContextConfigTest.gd` | `StageContextConfigTests.cs` |

테스트 우선순위:

1. 순수 C# 로직 테스트: input/action/spawn/fever/boss pattern/progress
2. PlayMode prefab smoke test: RunnerStage, BossStage, Main flow
3. 모바일 해상도 레이아웃 테스트: 1280x720, 16:9, 20:9
4. Android 빌드 smoke test

Unity 전환에서 가장 위험한 부분은 시각 차이가 아니라 판정과 타이밍 차이다. 따라서 스폰 타임라인, 입력 윈도우, 피버 지속 시간, boss pattern timeout은 숫자 테스트로 먼저 고정한다.

## 11. 위험 요소와 대응

| 위험 | 설명 | 대응 |
|---|---|---|
| 타이밍 차이 | Godot `_process`와 Unity `Update`의 delta 처리 차이 | 순수 로직은 delta 입력 테스트로 고정 |
| 입력 판정 차이 | 모바일 touch, mouse, UI raycast가 섞일 수 있음 | gameplay input surface를 별도 컴포넌트로 분리 |
| Sprite scale/pivot 차이 | Godot Sprite2D와 Unity SpriteRenderer 기준점 차이 | profile에 pivot/offset/target height 저장 |
| Collider 차이 | Area2D와 Collider2D/Trigger 처리 차이 | 액션존은 물리 충돌보다 명시적 bounds query 우선 |
| 저장 호환 | Godot ConfigFile과 Unity JSON 차이 | 새 앱이면 JSON으로 단순화, 필요 시 importer 별도 |
| 에셋 교체 비용 | Asset Store 에셋의 해상도/피벗/애니메이션 구조가 다름 | prefab/profile adapter를 둬 코드 의존 차단 |
| 범위 폭증 | Unity 전환 중 신규 기능을 같이 넣을 위험 | stage1 parity 전까지 신규 기능 금지 |

## 13. 실행 판단 기준

Unity 전환을 시작해도 되는 조건:

- Godot `main`이 제출본 기준으로 안정화되어 있다.
- Unity 작업이 별도 루트에서 시작되어 Godot 프로젝트를 깨지 않는다.
- 첫 목표가 신규 기능이 아니라 stage1 parity로 고정되어 있다.
- 현재 stage config 구조를 Unity 데이터 모델로 옮기는 데 동의한다.

Unity 전환을 미뤄야 하는 조건:

- 아직 Godot에서 스테이지 추가나 캐릭터 해금 구조를 빠르게 더 실험해야 한다.
- 에셋스토어 구매 에셋의 방향성이 정해지지 않았고, 그 에셋에 맞춘 게임성 변경이 예상된다.
- 제출 이후 안정화 버그가 많이 남아 있어 기준 동작 자체가 흔들리는 상태다.

현재 프로젝트 상태 기준으로는 Unity 전환을 시작해도 되지만, 첫 스프린트는 반드시 `Unity 프로젝트 생성 + 순수 로직 포팅 + RunnerStage parity`까지만 잡는 것이 안전하다. 보스 모션, UI polish, Asset Store 에셋 교체는 그 다음 단계로 미루는 편이 리스크가 낮다.
